# アプリ評価スキル

ユーザーが作ったアプリを「自分で評価する」のではなく、**サブエージェントに作業を任せ、メインは統合と最終フィードバックに徹する**。評価の偏りを避けるため、アプリを作った文脈を知らない独立したエージェントに評価させることが基本方針。

## 0. 入力の確認（メインで行う）

評価対象を特定する。以下のどれが手元にあるか確認し、足りなければ1回だけ質問する。
- ソースコード（リポジトリ / フォルダ / 添付ファイル）
- 動作するURL、またはローカルで起動する方法
- スクリーンショット・説明文・README
- 想定ユーザーと、アプリが解決したい課題（不明なら README やコードから推定し、推定であることを明記）

アプリの概要（何をするアプリか・対象ユーザー・主要機能・技術スタック）を5〜10行の「評価ブリーフ」にまとめる。これを各サブエージェントに渡す。

## 1. サブエージェントへの分担（並列で起動）

Agent ツールで以下の3つを**同じターンで並列に**起動する。各プロンプトには評価ブリーフ、対象ファイルのパス/URL、そして下記の担当範囲と出力形式をそのまま含める（サブエージェントはこの会話を見られない）。

### エージェントA: 品質評価（コード・動作）
担当: 完成度、ロバスト性、パフォーマンス、セキュリティ、保守性。
- コードを読み、可能なら実際にビルド・起動・テストを実行する
- 異常系を試す: 空入力、巨大入力、不正な値、ネットワーク断、連打、権限なし、想定外の順序操作
- エラーハンドリング、入力検証、秘密情報のハードコード、依存関係の古さ、テストの有無を確認
- 指摘には必ず根拠（ファイル名:行番号、再現手順、実行ログ）を付ける

### エージェントB: ユーザー体験評価
担当: ユーザーへの効果、使いやすさ、アクセシビリティ、オンボーディング。
- 想定ユーザーになりきって主要タスクを最初から最後まで通す（UIがあればブラウザで操作、なければコード/画面から導線を追う）
- ニールセンの10ヒューリスティクスでチェック
- 「初めて使う人が5分で価値を感じられるか」「何ステップで目的を達成できるか」を具体的に数える
- アクセシビリティ（コントラスト、キーボード操作、代替テキスト、モバイル表示）を確認

### エージェントC: 競合・類似サービス調査
担当: 市場比較と差別化。
- WebSearch / WebFetch で類似アプリ・サービスを5〜8件探す（直接競合、代替手段、無料/有料の両方）
- 各サービスの主要機能、価格、対象ユーザー、強み、弱み（レビューや評判から）を整理
- 対象アプリと同じ観点で比較表を作り、「対象アプリにしかない価値」と「競合に当たり前にあって対象アプリに欠けているもの」を明示
- 出典URLを必ず付ける。推測と事実を区別する

### 各エージェント共通の出力形式
```
## 担当観点ごとの評価
- 観点名: スコア(1-5) / 根拠 / 具体例
## 重大な問題（優先度順）
## 良い点
## 不確かな点・検証できなかったこと
```

## 2. 評価観点とスコア基準

| 観点 | 見るポイント |
|---|---|
| ユーザーへの効果・価値 | 課題を本当に解決しているか、既存手段より良いか、継続利用の理由があるか |
| 完成度（練度） | 機能の抜け、未実装箇所、見た目の仕上げ、細部の一貫性 |
| 使いやすさ（UX） | 学習コスト、導線の短さ、エラー時の案内、フィードバックの分かりやすさ |
| ロバスト性 | 異常入力・障害時の挙動、データ消失リスク、クラッシュの有無 |
| パフォーマンス | 起動・応答速度、重い処理、スケール時の懸念 |
| セキュリティ・プライバシー | 認証、入力検証、秘密情報管理、個人データの扱い |
| アクセシビリティ | 多様なユーザー・端末で使えるか |
| 保守性・コード品質 | 構造、可読性、テスト、ドキュメント |
| 差別化・市場性 | 競合と比べた独自性、選ばれる理由 |

スコア: 5=市販品レベル / 4=実用十分、軽微な改善点 / 3=使えるが明確な弱点 / 2=重要な問題あり / 1=基本機能に支障。
根拠のないスコアは付けない。検証できなかった観点は「未評価」とする。

## 3. 統合（メインで行う）

- 3エージェントの結果を突き合わせ、矛盾があれば根拠の強い方を採用し、必要なら該当箇所を自分で確認する
- 重複する指摘はまとめる
- サブエージェントが根拠を示していない指摘は除外するか「要確認」と明記する

## 4. 最終フィードバック

以下の構成でレポートにする（長く残すものなので Docs 型の成果物として作るのが基本。ユーザーが形式を指定したらそれに従う）。

1. **総評**（3〜5行）: 一言でいうとどんなアプリで、今どの段階にあるか
2. **スコアカード**: 観点別スコア表＋総合評価（レーダーチャートがあると望ましい）
3. **強み**: 伸ばすべき点
4. **重大な問題**: 優先度順、根拠と再現手順つき
5. **競合比較**: 比較表と差別化ポジションの分析
6. **改善ロードマップ**:
   - すぐ直すべき（1日以内・効果大）
   - 短期（1〜2週間）
   - 中長期（差別化・成長のため）
   各項目に「なぜやるか」と「期待される効果」を添える
7. **出典**: 競合調査のURL

フィードバックは率直に。褒めるだけ・けなすだけにせず、すべての指摘を具体的な次の行動につなげる。作者の努力ではなく、ユーザーにとっての結果で評価する。
