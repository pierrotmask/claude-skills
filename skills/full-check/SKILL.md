# チェック（簡易チェック／総チェック）

総チェックは時間とトークンを多く使う。**普段は簡易チェック**にし、次の条件のときだけ総チェックにする。

## 0. どちらにするかを決める

**総チェックにするのは、次のどれかに当てはまるときだけ：**

| 条件 | 例 |
|---|---|
| ユーザーが明示的に頼んだ | 「総チェックして」「フルチェック」「最後は総チェック」「チェックを怠るな」 |
| 大きな変更 | 下の「大きな変更の目安」に1つでも当てはまる |
| 小さな変更がたまった | 前回の総チェックのあと、小さな変更が **3回** たまった（今回の変更を含めて数える） |
| 総チェックの記録が見つからない | 下の「数え方」で、このアプリの記録が1つもない |

どれにも当てはまらなければ **簡易チェック**（1.）。迷ったら、どちらにしたかと理由を報告に書く。

**大きな変更の目安**
- 保存データの形・設定項目・マスターデータ・共有リンクの形式を変えた（`safe-data-change` スキルを使う変更）
- 新しい画面・タブ・機能を足した、または画面の構成を作り直した
- サービスワーカー・manifest・自動更新・引き継ぎなど PWA の仕組みを変えた（`pwa-single-file` スキル）
- 起動時の処理や、多くの画面が使う共通の関数を変えた
- 変更が多い（目安：差分が 150 行以上、または 3 画面以上にまたがる）

**小さな変更**：上に当てはまらないもの（文言・色・余白の調整、ボタン1つの追加、1画面の中の不具合修正など）。ユーザーの1回の依頼を1回と数える。

**数え方（セッションをまたいでも数えられるように、公開版のコミットに記録を残す）**
- 公開するときのコミットメッセージに、必ず次のどちらか1行を入れる（`publish-unique-tool` スキル）
  - `チェック: 総チェック`
  - `チェック: 簡易（総チェック後 n 回目）`
- 前回の総チェックからの回数は、unique-tool の履歴で調べる：
  ```bash
  cd unique-tool && git fetch --depth=100 origin main
  git log origin/main --format='%h %s%n%b' -- <app>.html | grep -m1 -n 'チェック: 総チェック'
  ```
  - 見つかった記録より新しい `チェック: 簡易` の数 ＋ このセッションでまだ公開していない小さな変更の数 ＝ たまった回数
- このセッションの中でも、簡易チェックを何回したかを覚えておき、報告に書く

## 1. 簡易チェック（変えた部分だけ）

Playwright で、**変えた要素とその周りだけ**を確かめる。テストスクリプトはスクラッチパッドに置く。

1. **構文と起動**：`<script>` の構文エラーがなく、開いてすぐの `pageerror` が 0
2. **変えた要素を実際に動かす**
   - 新しい・変えたボタンを押し、期待どおりに表示・動作すること
   - 取り消し・保存して再読み込み、がある操作ならそれも1回
   - 表示文字に `undefined` / `NaN` / `null` が出ないこと
3. **変えた画面のスクリーンショット**：ライトとダークを1枚ずつ撮り、**実際に画像を見て**崩れがないか確認する（幅 390px。文字が長くなる変更なら 320px も）
4. **関係するテストだけ**：変えた機能の既存テストがあれば、それだけまわす（全部はまわさない）

簡易チェックで次のことが分かったら、その場で総チェックに切り替える：
- 変えていない場所でエラーや表示崩れが出た
- 変更が思ったより広く影響していた

**簡易チェックの報告**（短く）
- 「簡易チェック（総チェック後 n 回目）」と書く
- 何を確かめたか、何回試して何件問題があったか
- 次に総チェックになる条件（例：「あと1回の小さな変更で総チェックになります」）

## 2. 総チェック

以下の 2-1〜2-8 をすべて行う。

Playwright（インストール済み。`require('playwright')`、`chromium.launch()`）で、実際の画面を動かして確かめる。テストスクリプトはスクラッチパッドに置き、アプリのファイルには混ぜない。

### 2-1. 構文と起動
- `<script>` の中身を `new Function(...)` に渡して構文エラーがないこと
- 開いてすぐの `pageerror` が0であること
  - 特に「Cannot access 'X' before initialization」に注意する
  - 起動時に動く処理（保存データの点検など）から、後ろで定義した `const` を使うと起きる

### 2-2. 新機能のテストを書く
変更ごとに専用のテストを1本書く。

**大量に試して数で確かめる**
- 自動生成・ランダムなものは、パターンを変えて数十〜数百回まわす
- 「条件違反が0件」かどうかを数える。例：60回試して60回とも条件どおり
- 組み合わせ（食材×味付け×人数）は全件まわす。表示文字に `undefined` / `NaN` / `{` / `}` / `null` が出ないこと

**画面の操作で確かめる**
- 新しいボタンを実際にクリックする
- 「取り消す」で元に戻ること
- 保存して再読み込みしても残ること

**境界値**
- 最小・最大の値（例：人数1と6）
- 押せない状態（disabled）のボタン
- 空の状態（ストック0、献立なし）

**共有・互換**
- 共有リンクは「作る → 読む」で往復して、元と一致すること
- 旧形式のリンクも読めること

### 2-3. 既存テストを全部まわす
- これまでのテストを全部まわし、すべて `errors []` であること
- **UI を変えてテストが失敗したら、まず原因がテスト側かアプリ側かを見極める**
  - ボタン名やセレクタが変わっただけなら、テストの操作手順を直す
  - アプリの不具合ならアプリを直す
- 時間がかかるテストは個別にまわす（1回のコマンドは約10分まで）

### 2-4. ランダム操作テスト（monkey）
4環境で約2,800回ずつ、表示中の `data-act` ボタンをランダムに押す。
- 4環境：ライト390px、ダーク320px、iPhone ホーム画面版、iPhone Safari
- 危険な操作はスキップする（全消去・インポート・更新適用など）
- 150回ごとに点検すること：
  - データの整合性（存在しない食材・味付けへの参照がない）
  - 表示に `undefined` / `NaN` が出ていない
  - 横はみ出し、ID の重複、スクロールが固まっていない
- 最後に再読み込みして、正常に開けること
- 新しい種類のデータを足したら、点検の条件も合わせて直す（例：定番レシピ入りの献立は baseId がなくても正常）
- ページが勝手に再読み込みされて止まったら、`framenavigated` を記録して原因を探す

### 2-5. 旧データ・壊れたデータ
- 変更前の形の保存データを localStorage に入れて開く。消えない・壊れない・新しい初期値が入ること（`safe-data-change` スキル）
- わざと壊した値を入れて開き、点検で修復されること（範囲外の数値、存在しない ID、型違い）

### 2-6. PWA・共有（http で配信して確認）
- `python3 -m http.server 8765` で公開版を配信する
- 次のテストをまわす：SW の scope と、オフラインで開けること・自動更新でデータが残ること・iPhone の引き継ぎ・Android のインストール・共有リンクの受け取り（`pwa-single-file` スキル）

### 2-7. スクリーンショットを目で見る
- 変えた画面をライト・ダーク・幅320pxで撮り、**実際に画像を見て**確認する
  - 文字のはみ出し、1文字ずつの折り返し、ボタンの詰まり、色の不具合がないか
- アニメーション中に撮らない（0.5秒ほど待ってから撮る）
- トーストやスクロール位置で、見たい部分が隠れていないかも確認する

### 2-8. 報告
- 何を何回試して、問題が何件だったかを数字で示す（例：「13,776通りで崩れ0件」「4環境・約11,400回でエラー0」）
- 再現しなかった失敗や、テスト側の問題として直したものも正直に書く
- 失敗が残っているときは「通った」と書かない
- 総チェックをしたこと、それで小さな変更の回数が 0 に戻ったことを書く
