# アプリの評価（サブエージェントで実行）

このスキルは**サブエージェントとして**動く。呼び出し元の会話は見えないので、必要なことはこの手順と引数（`$ARGUMENTS`）から自分で集める。

- 評価対象：`$ARGUMENTS`（ファイルパス・URL・アプリ名。空なら作業ディレクトリから探す）
- **評価だけをする。アプリのファイルは一切変更しない・コミットしない・公開しない**
- テスト用スクリプト・スクリーンショット・レポートはスクラッチパッド（なければ `/tmp/app-review/`）に置く
- 最後の返答（＝呼び出し元に返る内容）は「6. 報告の形」に従う

## 1. 対象を把握する

1. 対象のファイルを特定する
   - 引数があればそれを使う。空なら作業ディレクトリの `index.html`、`*.html`、`package.json`、README を探す
   - 候補が複数あって決められないときは、いちばん新しく更新されたものを選び、報告に「何を評価したか」を書く
2. ソースを**全部読む**（1ファイルアプリなら HTML/CSS/JS すべて）。README・コミット履歴（`git log --oneline -20`）があれば読む
3. 次をメモする
   - **誰の・どんな困りごとを解決するアプリか**（README やタイトル・画面文言から推定。推定なら「推定」と書く）
   - 主な機能の一覧、画面の一覧
   - データの保存先（localStorage・サーバーなど）、外部への通信、PWA かどうか

## 2. 実際に動かす（Playwright）

読むだけで採点しない。**必ず動かしてから**採点する。Chromium と Playwright は入っている（`require('playwright')`、インストールし直さない）。

1. **起動**：`pageerror`・`console.error` を集める。開いてすぐのエラー数を記録
2. **主な使い方を最初から最後まで**：初めて使う人のつもりで、いちばん大事な操作を一通り行う（入力 → 結果 → 保存 → 再読み込みで残るか）
3. **画面幅とテーマ**：390px（スマホ）・320px（小さいスマホ）・1280px（PC）、ライト／ダーク。スクリーンショットを撮り、**実際に画像を見て**判断する
4. **意地悪な操作（ロバスト性）**
   - 空欄・0・負の数・とても大きい数・長い文字列・絵文字・`<script>` などの記号を入れる
   - ボタンの連打、途中で再読み込み、戻る操作
   - localStorage に壊れたデータ（不正な JSON・古い形・型違い）を入れて開く
   - オフライン（`context.setOffline(true)`）で開く・操作する
   - ランダム操作を数十回して、エラーや `undefined` / `NaN` / `null` の表示が出ないか
5. **アクセシビリティ・性能の簡単な確認**
   - キーボードだけで主要操作ができるか、ボタンやフォームにラベルがあるか、文字のコントラスト、タップ領域の大きさ（目安 44px）
   - 読み込みにかかる時間、ファイルサイズ、重い操作での固まり

見つけた問題は「再現手順・期待した動き・実際の動き・スクリーンショット」をセットで記録する。

## 3. 採点する

各項目を **5点満点**で採点し、**必ず根拠（見たこと・試した結果）を書く**。根拠のない点数は付けない。確かめられなかった項目は「未確認」とし、理由を書く。

| # | 項目 | 見ること |
|---|---|---|
| 1 | 利用者への効果 | 困りごとを本当に解決するか。使う前と後で何が楽に・速く・正確になるか。続けて使いたくなる理由があるか |
| 2 | 完成度（練度） | 機能が最後まで作り込まれているか。中途半端な機能・仮の文言・使われないボタンがないか。細部の仕上げ |
| 3 | 使いやすさ | 初めてでも迷わないか。操作の手数、主役の分かりやすさ、日本語の自然さ、スマホ片手での操作 |
| 4 | ロバスト性 | 変な入力・連打・壊れたデータ・オフラインで壊れないか。エラー時に復帰できるか |
| 5 | データの安全・信頼性 | 入力したデータが消えないか、更新後も残るか、書き出し・バックアップ手段、計算結果の正しさ |
| 6 | 見た目・一貫性 | 配色・余白・文字の大きさがそろっているか、ライト／ダーク・画面幅で崩れないか |
| 7 | アクセシビリティ | キーボード操作、ラベル、コントラスト、文字サイズ変更への耐性 |
| 8 | 性能 | 起動の速さ、操作の反応、重さ |
| 9 | プライバシー・安全性 | 不要な外部通信がないか、入力をそのまま HTML に入れていないか（XSS）、秘密の情報がコードにないか |
| 10 | 独自性 | 類似サービスにない強みがあるか（4. の結果を使って採点） |

**点数の目安**
- 5：類似の有名サービスと並べても見劣りしない。直すところがほぼない
- 4：よくできている。小さな改善点がいくつかある
- 3：使えるが、はっきりした不満点がある
- 2：使うと困る場面が多い
- 1：主な目的を果たせない

対象によって合わない項目（例：サーバーのないアプリの認証）は「対象外」にしてよい。逆に、対象に大事な観点が表に無ければ（例：ゲームの面白さ・学習アプリの学習効果・計算ツールの正確さ）、**項目を足して**採点する。

## 4. 類似アプリ・サービスを調べて比較する

1. **探す**：WebSearch で、日本語と英語の両方で検索する（例：「〇〇 アプリ」「〇〇 ツール 無料」「〇〇 app」「best 〇〇 app 2026」）。App Store / Google Play / Web サービスを含める
2. **選ぶ**：代表的なものを **3〜5 個**。有名どころと、このアプリに近い小規模なものを混ぜる
3. **調べる**：公式サイト・ストアの説明・レビューを読む（WebFetch があれば使う）。各サービスについて、主な機能・料金・対応端末・評判（よい点／不満点）をまとめる
   - 調べて分かったことと推測は分けて書く。出典の URL を必ず残す
   - レビューで多い不満は、このアプリが勝てるポイントの候補としてメモする
4. **比較表を作る**：行＝比較する観点（主な機能・料金・登録の要否・オフライン・広告・データの持ち方・使い始めの手軽さ など）、列＝このアプリと類似サービス
5. **分析する**
   - このアプリが**勝っている点**（強み）
   - **負けている点**（類似サービスにあって、このアプリにない大事なもの）
   - **狙える隙間**（どのサービスも満たしていない需要）

## 5. フィードバックをまとめる

1. **総評**：3〜5行。誰に向けて、何がよくて、何がいちばん足りないか
2. **改善提案**を優先度順に並べる。各提案に次を付ける
   - 優先度：**高**（利用者が困る・データが消える・壊れる）／**中**（使いやすさ・完成度が上がる）／**低**（あればうれしい）
   - 手間の目安：小（数行）／中（1機能）／大（作り直し）
   - 理由：どの採点項目・どの不具合・どの類似サービスとの比較から来た提案か
   - 具体的な直し方（どの画面のどこを、どう変えるか）
3. 「**まず1つだけ直すならこれ**」を1つ選ぶ
4. よいところも具体的に書く（残すべき点を分かるようにする）

提案は、作り手が次の依頼でそのまま使えるくらい具体的にする。抽象的な一般論（「UXを改善する」など）だけの提案は書かない。

## 6. 報告の形

詳しいレポートを `app-review-<アプリ名>-<日付>.md` としてスクラッチパッドに保存し、**呼び出し元への返答**は次の形で短くまとめる（返答だけで内容が分かるようにする）。

```
## 評価対象
<ファイル／URL>、<推定した目的と利用者>

## 採点（5点満点）
| 項目 | 点 | ひとこと根拠 |
|---|---|---|
| 利用者への効果 | 4 | ... |
| ...（10項目＋足した項目） | | |
| 平均 | 3.8 | |

## 見つかった不具合
- [高] <内容>（再現：...）
- ...（なければ「なし」）

## 類似サービスとの比較
| 観点 | このアプリ | A | B | C |
|---|---|---|---|---|
強み：... ／ 弱み：... ／ 狙える隙間：...
出典：<URL の一覧>

## フィードバック
総評：...
まず直すならこれ：...
1. [高・小] ...
2. [中・中] ...
残すべきよい点：...

詳細レポート：<保存したファイルの絶対パス>
スクリーンショット：<フォルダの絶対パス>
確かめられなかったこと：...
```
