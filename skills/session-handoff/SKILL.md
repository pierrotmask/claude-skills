# 新しいセッションへの引き継ぎ

会話が長くなると、前半の内容は要約されて細部が失われ、動きも遅くなる。区切りのよいところで新しいセッションに移ると、続きを正確に早く進められる。

## 移るべきかの目安
- 会話の要約が1回でも起きた（2回目以降は特におすすめ）
- 依頼が1つ終わり、次の依頼が別の話題になる
- 移らないほうがよい：作業の途中（テストが通っていない・公開前）。終わらせてから移る

## 手順
1. **作業を終わらせる**
   - 変更が残っていれば、チェック（`full-check`）→公開（`publish-unique-tool`）まで済ませる
   - 開発リポジトリをコミットし、作業ブランチに push（`git status` が空になること）
   - テストの出力ファイル（例：`imp_bk.json` の変化）は元に戻す。スクリーンショットは .gitignore 済み
2. **引き継ぎメモを更新する**（開発リポジトリの `HANDOFF.md`。LiftCanvas なら `liftcanvas-src/HANDOFF.md`）
   - 見出しの日付と公開版の番号
   - 「0. 新しいセッションの始め方」：貼るだけの依頼文、最初の準備コマンド、**直近の総チェックの版と、その後の簡易チェックの回数**
   - 「2. 完了した内容」の表に今回の版を追加（新しい順）
   - 「3. 未完了タスク」：利用者に聞いて保留中のことも書く
   - 「4. 変更したファイル」：今回分に置き換える（古い分は表に残っていれば消してよい）
   - 「5. 設計判断」：利用者が決めたこと・指定したことは理由と一緒に必ず残す
   - 「6. 残っている問題」
   - 長くなりすぎたら、古い細部を削って短く保つ（新しいセッションが最初に全部読むため）
3. **もう一度コミット・push** して、作業ブランチに最新の HANDOFF が入っていることを確かめる
4. **利用者に伝える**（日本語・平易に）
   - 新しいセッションの始め方：同じ環境・同じリポジトリで新しいセッションを開き、次の依頼文を貼る
   - 依頼文はコードブロックにして、そのままコピーできるようにする
   - 例：
     ```
     liftcanvas-src/HANDOFF.md を読んでから、LiftCanvas の作業を続けて。作業ブランチは <作業ブランチ>。公開先は pierrotmask/unique-tool。
     ```
   - 古いセッションは、新しいセッションが動き出したら閉じてよい（記録はすべて push 済み）

## 新しいセッション側で最初にやること（HANDOFF の 0 節に書いておく）
- 作業ブランチを fetch して checkout（新しいセッションには別の名前のブランチが割り当てられることがある。その場合は前の作業ブランチを取り込んでから続ける）
- 公開先リポジトリ（unique-tool）を追加して clone
- 依存の install、テスト用サーバーの起動、組み立てが通ることの確認

## 気をつけること
- 個人情報・利用者の実際の記録は HANDOFF に書かない
- コミット・PR・HANDOFF にモデル名を書かない
- 依頼文には秘密の値（鍵・トークン）を入れない
